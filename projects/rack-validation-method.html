How I validate a rack

A rack-scale AI system leaves the factory only after it has passed every station on the test line. This is that line, station by station: what each one checks, what “pass” means, and the failures it exists to catch. The hardware I work on is under NDA, so this covers the method, not the product.

  • NPI (EVT/DVT/PVT)
  • PXE
  • Run-in
  • NVLink
  • RDMA/RoCE
  • PRBS/SerDes
  • Redfish
  • IPMI
  • Python

01Why a test line

A training job on a rack is only as healthy as its weakest link. One GPU that drops out of the fabric, one memory channel that throws errors under heat, one firmware image a version behind, and a job built for 72 GPUs stalls or runs short. Customers find those problems at the worst possible time, so the factory has to find them first.

It does that with a fixed sequence of stations. Each one assumes the stations before it passed, so a failure points at a small set of causes instead of the whole rack. The same line runs at every development build (EVT, DVT, PVT) and then in mass production, which is what makes results comparable from build to build.

02The line, station by station

Select a station to see what it does, or run the whole line. Turn on Show a failure to watch what happens when a rack fails partway through.

PXE boot Boot every blade from the network

Before any test runs, every compute blade boots over the network. It pulls the test operating system from a provisioning server, boots it, and checks in. Nothing is installed by hand, so every rack starts from the same known image.

What it checks

  • Every blade gets an address and finds the boot server
  • The right image and version download and boot
  • Every blade is reachable and reports in

Pass means

Every blade in the rack is running the expected image and answering.

What it catches

A wrong boot order, a dead network port, a blade that never shows up.

Pretest Check every part on every compute blade

Component-level testing on each compute blade. Firmware is flashed to the versions this build is meant to run, then every part is checked on its own: CPUs, memory, PCIe links, SSDs, GPUs and other ASICs, the data buses that connect them, and the sensors that watch them.

What it checks

  • Inventory matches the bill of materials
  • BIOS, BMC, CPLD, NIC and GPU firmware at target versions
  • Every PCIe link trains at its expected width and speed
  • Every device answers on its bus; every sensor reads and is in range

Pass means

Each blade is exactly what the build says it should be, part by part.

What it catches

A missing DIMM, a link that trained at x8 instead of x16 or a generation slow, a mis-seated SSD, a firmware mismatch.

Run-in Stress the rack until weak parts fail here

Hours of stress across CPUs, memory, SSDs and GPUs at once. Pretest proves a part works; run-in proves it keeps working when it is hot and busy. Weak parts tend to fail early in their life, and run-in is where that early life gets spent.

What it checks

  • Full load on CPU, memory, storage and GPUs together
  • Temperatures and power stay within limits
  • Memory and PCIe error counters stay clean
  • No hangs, resets or dropped devices

Pass means

The whole run finishes with no uncorrectable errors and corrected errors under threshold.

What it catches

Marginal memory, parts that fail young, cooling problems, links that drop only under load.

Network blade Connect the compute blades to each other

Until now each compute blade has been tested alone. Here they start talking to each other, through the network blades and the cable cartridge, the dense bundle of cables at the back of the rack that wires every compute blade to every network blade.

What it checks

  • Every link through the cable cartridge trains
  • Every network blade sees every compute blade
  • Every GPU joins the fabric: on a 72-GPU rack, all 72

Pass means

The rack works as one machine, not as a stack of separate blades.

What it catches

A badly seated cartridge, a bent pin, a single bad lane, network-blade firmware problems.

Nettest Test the network itself

With everything connected, the network gets tested as a network: every NIC, every port, every path the rack will use to talk to the rest of the cluster. RDMA/RoCE traffic runs between every pair, and error counters are watched through a soak.

What it checks

  • Every port links up at the right speed and width
  • RDMA bandwidth between every NIC pair
  • Latency under load
  • Link error counters after a soak

Pass means

Every path performs to target and stays clean under sustained traffic.

What it catches

Bad cables or optics, NIC firmware and configuration problems, marginal SerDes lanes. PRBS testing on a suspect lane separates the channel from the device.

FST Final system test, then factory defaults

One last pass over the things most likely to have drifted while the rack was being tested and debugged: firmware versions, sensors and data buses. Then the rack is set back to its default settings, so the customer gets a clean machine, not a test fixture.

What it checks

  • Firmware matches the ship manifest
  • A final sensor and data-bus sweep
  • Out-of-band management works over Redfish and IPMI
  • Default settings applied, test settings removed

Pass means

The rack matches its ship configuration exactly.

What it catches

A setting left behind by debugging, a part swapped during repair without a re-check, a firmware image that never got re-flashed.

Ship Released to the customer

Every station passed, in order, on this rack. Its results are on record next to every other rack from the same build, which is what turns a single pass into evidence that the build is ready for mass production.

03Why the order matters

Every station leans on the one before it. Nettest is meaningless if a NIC trained a generation slow in pretest, and a GPU missing from the fabric at the network blade looks like a fabric problem but is often a link problem underneath. Passing in order means a failure at any station points to that station’s layer, not to everything at once.

It also decides where a repaired rack goes next. A fix can disturb anything it touched, so a repaired rack goes back through the line from an earlier station, not straight to the one it failed. That is the loop the demo above shows when you turn on Show a failure.

04A failure, walked through

A representative example of the kind of failure the line exists for. It’s built from the class of problem, not from one program’s details.

  1. SymptomAt the network blade station, one GPU on a few racks fails to join the fabric after a cold boot. A warm reboot sometimes fixes it, which is the worst kind of failure: it passes a quick re-test.
  2. HypothesesA marginal link on that GPU’s path through the cable cartridge, a firmware race at power-on between the BMC, CPLD and GPU baseboard, or a stale fabric configuration left on the node.
  3. IsolationRule out the setup first: re-provision over PXE and read the fabric logs from the start. Then run PRBS on the affected lanes, swap the blade into a known-good slot to see whether the fault follows the part or the position, and repeat cold boots with BMC and serial-console logs captured on every cycle.
  4. Root causeThe fault stays with the position and only appears on cold boot: a power-sequencing timing problem that leaves some links not ready when fabric initialization starts.
  5. FixThe timing fix goes to the firmware team for the next release candidate, with reproduction steps and logs attached, and is verified on the next build.
  6. PreventionA cold-boot loop that checks every GPU has joined the fabric is added to the automated suite, so a regression shows up on the first rack of the next build.

05Where automation fits

The line is only as good as its consistency. I write Python and Bash checks and a Python/YAML test framework that run the same suite the same way on every rack, parse the logs, and flag anything outside its limits. Every failure should leave enough behind to start debugging without re-running the test. On my current program that has automated about 60% of what used to be manual rack checks.
