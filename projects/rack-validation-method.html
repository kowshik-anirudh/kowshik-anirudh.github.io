How I validate a rack

How I take a rack-scale AI system from bring-up to a build that can go to mass production. The hardware I work on is under NDA, so this page covers the method and the class of problem, not the product.

  • NPI (EVT/DVT/PVT)
  • PXE
  • PRBS/SerDes
  • PCIe
  • RDMA/RoCE
  • NVLink
  • Redfish
  • IPMI
  • Python

01Why rack-level validation matters

Large AI training and inference jobs depend on every GPU and every link in a rack working correctly. Validation is where link, connectivity, configuration and firmware problems get caught, before they reach a production cluster.

A rack goes through each development phase (EVT, DVT, PVT) on the way to mass production. Each build is gated by test plans, firmware validation and failure debug, and fixes go back to the hardware and firmware teams so they land in the next board rev or firmware release candidate.

02The method, from the bottom up

  1. ProvisionPXE network boot provisions multi-host test environments for L10–L12 rack bring-up.
  2. SignalsPRBS/SerDes testing isolates PCIe, NIC, NVMe and retimer link failures.
  3. FabricRDMA/RoCE across NICs, network modules and the full rack topology, and the NVLink switch fabric through NVIDIA Fabric Manager, until every GPU has joined.
  4. FirmwareBMC validation over Redfish, IPMI, SOL and out-of-band management: sensors, telemetry and BMC–BIOS/CPLD/BIC interactions.
  5. AutomationPython/Bash checks, a Python/YAML test framework and log parsing, so results are repeatable from build to build.

The order is the point. Every layer depends on the one below it, so a failure is only meaningful once everything underneath has passed. A GPU missing from the NVLink fabric looks like a fabric problem but is often a link that trained one generation slow. Pass means something concrete at each layer:

  • Provision: every node PXE-boots the expected image, and its inventory (CPUs, GPUs, NICs, drives, firmware versions) matches the build’s bill of materials.
  • Signals: every PCIe link trains at the expected width and speed, and PRBS runs error-free on every lane for the full soak time.
  • Fabric: every GPU joins the NVLink domain, and RDMA bandwidth and latency between every pair of NICs is within target.
  • Firmware: every Redfish and IPMI sensor reports and stays in range, power and reset actions work out of band, and SOL captures a full boot.
  • Automation: the same suite runs clean on every build, and every failure leaves logs good enough to start debugging without re-running it.

03A failure, walked through

A representative example of the kind of failure this method exists for. It's built from the class of problem, not from one program’s details.

  1. SymptomAfter a cold boot, one GPU on a few racks fails to join the NVLink fabric. A warm reboot sometimes fixes it, which is the worst kind of failure: it passes a quick re-test.
  2. HypothesesA marginal link on that GPU’s path to the switch tray, a firmware race at power-on between the BMC, CPLD and GPU baseboard, or a test-setup problem such as a stale fabric configuration on the node.
  3. IsolationRule out the setup first: a clean re-provision over PXE, and Fabric Manager logs read from the start. Then run PRBS on the affected lanes, swap the GPU’s slot with a known-good one to see whether the fault follows the part or the position, and repeat cold boots with BMC and SOL logs captured on every cycle.
  4. Root causeThe fault stays with the position, not the part, and only on cold boot: a power-sequencing timing problem that leaves some links not ready when fabric initialization starts.
  5. FixThe timing fix goes to the firmware team for the next release candidate, with the reproduction steps and logs attached, and is verified on the next build.
  6. PreventionA cold-boot loop with a check that every GPU has joined the fabric is added to the automated suite, so a regression shows up on the first build, not in production.

04What I'd check first

When a rack doesn't come up cleanly, these are the first things I look at, in order.

  • Does every node boot the expected image, and does its inventory match the build’s bill of materials?
  • Do all PCIe links train at the expected width and speed, including through retimers?
  • Are the BMC sensors in range, and do the SEL and SOL logs show anything during power-on?
  • Are BIOS, BMC, CPLD and NIC firmware at the versions this build is meant to run?
  • Does every GPU show up, and does every one join the NVLink fabric?
  • Does RDMA/RoCE work between every pair of NICs, at the expected bandwidth?
  • Does the fault follow the part or the position when I swap it?
  • Does it reproduce on a cold boot, or only on a warm one?
